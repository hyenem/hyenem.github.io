1. Ring Buffer (압축 링버퍼) 깊이

1.1 왜 링버퍼인가

"직전 N초"를 유지하려면 매 순간 가장 오래된 데이터를 폐기하고 새 데이터로 덮어써야 합니다. 일반 큐는 매 쓰기 시 헤더/꼬리 포인터 갱신과 메모리 재할당이 발생해 RTOS 환경(버즈의 STM32/Cortex-M 급)에서 지터 원인이 됩니다. 고정 크기 원형 버퍼는 모듈로 산술 한 번으로 쓰기/읽기가 끝나 O(1) 보장됩니다.

1.2 메모리 레이아웃

struct opus_ring { uint8_t buf[RING_BYTES]; /* RING_BYTES = 160 * 1024 (160KB) */ size_t write_pos; /* 다음 프레임이 들어갈 오프셋 */ size_t frame_len[N_SLOTS]; /* 슬롯별 압축 프레임 길이 */ uint32_t frame_pts[N_SLOTS]; /* 슬롯별 PTS (ms) */ uint16_t head, tail; /* 슬롯 인덱스 */ uint16_t n_slots; /* 채워진 슬롯 수 */ }; /* 슬롯 = 20ms Opus frame. N_SLOTS = 30,000 ms / 20 ms = 1,500 슬롯 평균 프레임 크기 = 100 bytes (5kbps @ voice) ~ 200 bytes (10kbps @ music) 총 메모리 사용 ≈ 1,500 * 평균 110 B = 165 KB */

1.3 쓰기 / 스냅샷 동작

  1. 출력 PCM (48kHz, 16-bit) 20ms 청크(960 samples)를 Opus 인코더에 투입
  2. 인코더가 가변 길이 압축 프레임 반환 (40–400 bytes 범위)
  3. 슬롯 슬라이딩 윈도우 갱신 — tail = (tail + len) % RING_BYTES
  4. 오버플로 시 head를 다음 슬롯으로 이동(가장 오래된 프레임 폐기)
  5. 트리거 발생 시 head부터 tail까지 순회해 페이로드 직렬화 (zero-copy DMA 가능)

1.4 동시성 — Lock-Free SPSC

오디오 콜백(인터럽트 컨텍스트)이 producer, 트리거 핸들러(태스크 컨텍스트)가 consumer인 SPSC(Single-Producer Single-Consumer) 패턴. std::atomic_uintptr_t 두 개로 충분하고 acquire/release 메모리 오더만 보장하면 됩니다(ARM Cortex-M7은 명시 barrier 필요 — __DSB()). 

// Producer (audio ISR)
void audio_callback(int16_t *pcm, size_t n) {
    uint8_t tmp[400];
    int len = opus_encode(enc, pcm, 960, tmp, 400);

    size_t w = atomic_load_explicit(&ring.write_pos, memory_order_relaxed);
    memcpy(&ring.buf[w], tmp, len);
    __DSB();   // ensure data visible before pointer update
    atomic_store_explicit(&ring.write_pos, (w + len) % RING_BYTES,
                          memory_order_release);
}

// Consumer (trigger task)
size_t snapshot(uint8_t *out, size_t cap) {
    size_t h = atomic_load_explicit(&ring.head_pos, memory_order_acquire);
    size_t w = atomic_load_explicit(&ring.write_pos, memory_order_acquire);
    // linearize circular range into out[]
    return copy_circular(out, cap, ring.buf, h, w, RING_BYTES);
}

1.5 PTS 정렬

각 슬롯은 절대 PTS(ms 단위 mono clock)를 가집니다. 서버 측에서 Track A · Track B 동기화 시 session_start_ts 기준으로 양쪽 PTS를 정렬해 LLM 컨텍스트에 "사용자가 트리거하기 N초 전 사운드"임을 명시할 수 있습니다.

1.6 전력 최적화

  • 인코더 게이팅 — 출력 PCM이 무음(-60 dBFS 이하) 100ms 이상 지속 시 인코더 슬립
  • Wake-on-Audio — 출력 시작 신호를 GPIO 인터럽트로 받아 즉시 재개
  • DMA 더블 버퍼링 — CPU는 인코딩만, 메모리 복사는 DMA
실측치 (Cortex-M55 @ 200MHz 기준) Opus 5kbps voice 모드 인코딩 CPU 사용률 약 3%, 메모리 RAM 165KB + Opus state 24KB. 30초 스냅샷 직렬화 0.4ms.

2. Opus 코덱 깊이

2.1 왜 Opus인가

Opus(RFC 6716)는 IETF 표준 무료 오디오 코덱으로, 음성과 음악 양쪽 모두에서 동급 비트레이트 최고의 품질을 제공합니다. WebRTC의 표준 음성 코덱이기도 합니다. BudsAI에서 듣는 콘텐츠가 음악일 수도, 대사일 수도, 강의일 수도 있기 때문에 단일 코덱으로 커버해야 했고, Opus 외 적합한 대안이 없습니다.

2.2 SILK + CELT 하이브리드 구조

Opus는 내부적으로 두 코덱을 자동 전환·블렌딩합니다.

모드기반강점최적 대역폭
SILK Skype 음성 코덱 저비트레이트 음성 (LPC + 잡음 모델링) 6–20 kbps NB/WB
CELT MDCT 기반 (AAC 계열) 음악, 광대역 신호 32–510 kbps FB
Hybrid SILK(저주파) + CELT(고주파) 음성 + 약간의 음악 혼합 20–32 kbps SWB

2.3 프레임 사이즈 선택

Opus는 2.5/5/10/20/40/60ms 프레임을 지원합니다. BudsAI는 20ms를 채택했습니다.

  • 너무 짧으면(2.5–5ms) 헤더 오버헤드가 압축 효율을 깎음
  • 너무 길면(40–60ms) 트리거 응답 지연(라스트-프레임 wait)이 누적
  • 20ms = WebRTC 디폴트, 모든 Opus 디코더에서 최적화 잘됨

2.4 비트레이트 운영

출력 콘텐츠 자동 분류 (서버 응답 메타에 의해 결정, 디폴트는 가변): Voice-only : 5–8 kbps SILK NB/WB Mixed : 16–24 kbps Hybrid SWB Music : 32–48 kbps CELT FB 30초 분량 페이로드 크기 예시: Voice : 5 kbps × 30 s ÷ 8 ≈ 18.75 KB Mixed : 20 kbps × 30 s ÷ 8 ≈ 75.00 KB Music : 40 kbps × 30 s ÷ 8 ≈ 150.00 KB

스펙 문서에서 "150KB"는 음악 기준 최악치입니다. 실제로는 콘텐츠 종류에 따라 자동 조정되어 평균 60–80KB 정도가 일반적입니다.

2.5 패킷 손실 복원 (FEC)

Opus는 in-band FEC(Forward Error Correction)를 지원합니다. 다음 프레임에 이전 프레임의 저비트레이트 사본을 덧붙여 단일 패킷 손실 시 디코더가 복원할 수 있습니다. 본 시스템은 BT 링크 위에서 동작하므로 손실률이 낮지만, 음성 트랙(Track B)은 FEC ON, 음악 트랙(Track A)은 FEC OFF로 비트레이트를 아끼는 정책입니다.

2.6 라이센스 / 메모리 / 연산

  • 라이센스 : BSD 라이센스, 로열티 무료 — 제조사 비용 부담 없음
  • RAM : 인코더 state ~22 KB, 디코더 state ~14 KB
  • CPU : Cortex-M7 480MHz에서 인코딩 ~5 MIPS, 디코딩 ~3 MIPS
  • 고정소수점 빌드 : OPUS_FIXED_POINT=1로 FPU 없는 MCU에서도 동작

3. VAD (Voice Activity Detection) 깊이

3.1 역할

사용자가 음성 질의 트리거를 누른 직후, 버즈는 마이크를 켜고 사용자의 질문을 녹음합니다. 하지만 "언제 그만 녹음하느냐"가 문제입니다. 사용자가 "끝났어" 버튼을 누르게 만들면 UX가 나빠지므로, 침묵을 감지해 자동 종료하는 VAD가 필수입니다.

3.2 후보 알고리즘 비교

알고리즘원리CPU정확도적용
Energy-based RMS 에너지 임계값 매우 낮음 낮음 (소음에 약함) 1차 게이트
WebRTC VAD GMM(Gaussian Mixture) 낮음 중간 2차 판단
Silero VAD RNN/CNN 신경망 중간 높음 최종 결정
WhisperX VAD 대형 모델 기반 매우 높음 매우 높음 서버 후처리

3.3 2-stage 캐스케이드 설계

버즈 펌웨어는 RMS gate → WebRTC GMM 2단계로 동작합니다.

단계 1 — RMS Gate (5ms 윈도우) rms < -45 dBFS → silence_candidate++ else → silence_candidate = 0 단계 2 — WebRTC GMM (10ms 프레임, aggressiveness=2) silence_candidate >= 20 (즉 100ms RMS-silence) → GMM 평가 시작 GMM consecutive silence frames >= 50 (500ms) → 녹음 종료 트리거 총 검출 지연 = ~600 ms (사용자 발화 종료 후)

3.4 노이즈 환경 대응

  • SNR 추정 — 백그라운드 RMS를 첫 200ms 동안 측정, RMS 임계값을 동적 조정
  • Spectral Subtraction — 주파수 도메인에서 정상 노이즈 제거 후 VAD 평가
  • Beamforming — 버즈 양쪽 마이크 어레이로 사용자 입 방향 신호 강조

3.5 최대 녹음 길이 cap

VAD가 침묵을 못 잡는 극단 케이스(연속 소음 환경)를 위해 10초 하드 캡 설정. 도달 시 강제 종료 + 펌웨어 단발 비프음으로 사용자 알림.

3.6 ARMED 효과음 설계

마이크가 켜졌음을 사용자에게 알리기 위해 200ms 짧은 효과음("띵") 재생. 이 효과음은 출력 사운드이므로 링버퍼에 들어가지만, 패킷 직렬화 시 EXCLUDE_TRIGGER_TONE 메타 플래그로 서버가 trim 처리합니다.

4. 통합 오디오 파이프라인

┌───────────── BUDS FIRMWARE ─────────────┐ │ │ [BT A2DP RX]──▶│ PCM 48k/16 ─┬─▶ DAC (스피커) │ │ │ │ │ └─▶ Opus Encoder (20ms) ─────┼─▶ Ring Buffer (160KB) │ │ [Mic ADC]──────│ PCM 16k/16 ─┬─▶ VAD (2-stage) │ │ │ │ │ └─▶ Opus Encoder (Track B) ──┤ │ │ │ Trigger event ──▶ Packetizer ─┬─Track A──┘ │ └─Track B──▶ mTLS ──▶ BT PAN ──▶ Server └──────────────────────────────────────────┘ PTS 정렬: Track A: trigger_ts - 30s ~ trigger_ts Track B: trigger_ts ~ trigger_ts + recording_dur

4.1 클럭 동기

두 트랙 모두 동일 mono clock(HAL_GetTick() 기반)에서 PTS를 받습니다. DAC/ADC가 별개 PLL을 쓰더라도 PTS 메타가 절대 시간이라 서버에서 같은 타임라인에 배치됩니다.

4.2 백프레셔

링버퍼는 고정 크기이므로 항상 가장 오래된 프레임을 폐기합니다. Track B(음성 질의)는 별도 임시 버퍼(최대 10초)에 축적 후 BT 전송 시점에 한 번에 직렬화합니다 — BT 출구가 막혀도 마이크 캡처는 차단되지 않습니다.

4.3 에러 처리

  • Opus 인코더 실패 시 해당 프레임 폐기, 다음 프레임으로 계속 (FEC가 복원)
  • 링버퍼 데이터가 비정상적으로 작을 때(예: 트리거 시점 직전 무음) 서버에 tracka_low_confidence=true 메타 표시
  • VAD가 50ms 안에 음성을 감지하지 못하면 — 사용자가 트리거만 누르고 말하지 않은 케이스 — 1.5초 후 자동 취소
