1. 위협 모델

BudsAI 시스템에서 우리가 방어해야 할 적과 자산을 명시합니다.

1.1 자산

  • 오디오 페이로드 — 사용자가 듣던 사운드, 사용자가 한 질문 음성
  • 사용자 신원 — 디바이스 ↔ 계정 매핑
  • 디바이스 비밀키 — 시스템 신뢰의 루트
  • 세션 히스토리 — 서버 측 사용자 기록

1.2 위협 행위자

적능력주된 위협대응
네트워크 도청자 호스트 → 서버 트래픽 sniff 오디오 페이로드 노출 TLS 암호화 (BNEP 위 TCP/TLS)
악성 호스트 버즈가 페어된 폰/노트북이 악성 페이로드 가로채기 / 변조 버즈가 mTLS 종단점 (호스트는 못 봄)
가짜 서버 (MITM) DNS 하이재킹 / 라우트 조작 버즈가 가짜 서버로 전송 인증서 핀닝 + 서버 인증서 검증
물리 공격자 버즈 분해, 칩 디캡 디바이스 비밀키 추출 Secure Element (탬퍼 저항)
리플레이 공격자 이전 mTLS 세션 재전송 가짜 요청 위장 TLS 핸드셰이크의 random nonce + JWT exp
봇넷 / 대량 자동화 API 무한 호출 서비스 거부 / 비용 폭발 rate limit + 디바이스별 quota

2. TLS 1.3 기본기 (배경)

mTLS를 이해하기 전, TLS 1.3 일반 흐름을 짧게 정리합니다. (TLS 1.3, RFC 8446)

Client Server | ClientHello (key_share, cipher_suites, sni) | |─────────────────────────────────────────────────────▶ | | | | ServerHello (key_share, selected_cipher) | | {EncryptedExtensions} | | {Certificate} ←─ 서버 인증서 체인 | | {CertificateVerify} | | {Finished} | |◀──────────────────────────────────────────────────── | | | | {Finished} | |─────────────────────────────────────────────────────▶ | | | | ===== Application Data (AEAD encrypted) =========== | |◀═════════════════════════════════════════════════════▶| {...} = AEAD 암호화된 핸드셰이크 메시지 TLS 1.3은 1-RTT 핸드셰이크 (0-RTT 옵션은 보안 트레이드오프)

2.1 핵심 차이 (TLS 1.2 대비)

  • 전방위 비밀성(Forward Secrecy) 의무 — ECDHE만 허용, RSA key exchange 폐기
  • AEAD 의무(AES-GCM, ChaCha20-Poly1305) — CBC + MAC 제거
  • 핸드셰이크 메시지 암호화 (Server Cert까지 암호화 → 신원 노출 최소)
  • 1-RTT 기본 — 라운드 트립 1번에 핸드셰이크 완료

2.2 cipher suite 선택 (BudsAI)

TLS_AES_128_GCM_SHA256          // 디폴트, MCU AES 가속기 사용
TLS_CHACHA20_POLY1305_SHA256    // AES 가속기 없는 폴백

키 교환은 X25519(Curve25519 ECDHE) 단일 — 작은 코드, 빠른 연산, 안전.

3. mTLS (Mutual TLS) 깊이

3.1 일반 TLS와의 차이

일반 TLS는 클라이언트가 서버를 검증합니다(서버 인증서로). mTLS는 그 반대도 합니다 — 서버도 클라이언트의 인증서를 요구·검증합니다. 결과적으로 양쪽이 서로 신원을 증명.

3.2 mTLS 핸드셰이크

Buds Server | ClientHello | |─────────────────────────────────────────────────────▶| | ServerHello | | {EncryptedExtensions} | | {CertificateRequest} ←─ 클라 인증서 요구! | | {Certificate} ←─ 서버 자기 인증서 | | {CertificateVerify} | | {Finished} | |◀─────────────────────────────────────────────────────| | {Certificate} ←─ Buds 자기 인증서 | | {CertificateVerify} ←─ private key 서명 증명 | | {Finished} | |─────────────────────────────────────────────────────▶| | === Application Data === | |◀════════════════════════════════════════════════════▶|

3.3 BudsAI에서 사용하는 인증서 형식

// 디바이스 인증서 (X.509 v3, DER 인코딩)
Subject:        CN=buds-3a7f2e91-c4d8, O=Samsung Electronics
SerialNumber:   12345678901234567890
Issuer:         CN=BudsAI Device Sub-CA G1
Validity:       2026-01-01 ~ 2036-01-01 (10년)

SubjectPublicKeyInfo:
  Algorithm:    ECDSA P-256
  Public Key:   04 6f 8e 12 ...

X509v3 Extensions:
  Subject Alternative Name: buds-3a7f2e91-c4d8.devices.budsai
  Key Usage:                Digital Signature
  Extended Key Usage:       TLS Client Authentication
  Authority Key Identifier: ...

Signature Algorithm:        ecdsa-with-SHA256
Signature:                  30 45 02 21 ...

3.4 검증 단계 (서버 측)

  1. 버즈가 보낸 인증서 체인을 받는다 (Leaf + Sub-CA, Root는 서버가 보유)
  2. 체인 검증 — 각 단계 서명 확인, 만료 확인, 폐기 확인(CRL/OCSP)
  3. Leaf 인증서의 CN/SAN을 디바이스 등록 DB와 매칭
  4. CertificateVerify의 서명을 Leaf 공개키로 검증 — "이 인증서를 든 자가 진짜 개인키를 가졌는지" 증명
  5. JWT 같은 추가 인증과 매칭 — 디바이스 ID ↔ 계정 매핑 확인

3.5 mbedTLS 통합

// 클라(버즈) 측 — mbedTLS 설정
mbedtls_ssl_conf_authmode(&conf, MBEDTLS_SSL_VERIFY_REQUIRED);
mbedtls_ssl_conf_min_tls_version(&conf, MBEDTLS_SSL_VERSION_TLS1_3);

// 서버 루트 CA 적재 (펌웨어에 임베드)
mbedtls_x509_crt_parse(&server_ca,
                       server_root_ca_pem,
                       sizeof(server_root_ca_pem));
mbedtls_ssl_conf_ca_chain(&conf, &server_ca, NULL);

// 디바이스 자기 인증서 + private key (SE에서 핸들로 받음)
mbedtls_pk_setup_opaque(&device_pk, se_key_handle);
mbedtls_ssl_conf_own_cert(&conf, &device_cert, &device_pk);

// 핸드셰이크 진행 — SE가 ECDSA sign 호출을 가로채 칩 내부에서 서명
mbedtls_ssl_handshake(&ssl);

핵심은 mbedtls_pk_setup_opaque — 개인키가 RAM에 노출되지 않고 SE 안에서만 사용됩니다.

4. PKI 계층 & 인증서 발급

4.1 인증서 체인

┌──────────────────────────────────┐ │ BudsAI Root CA │ │ - 오프라인 HSM 보관 │ │ - 25년 유효 │ │ - 1회 발급 후 봉인 │ └──────────┬───────────────────────┘ │ 서명 ┌──────────────┴───────────────┐ ▼ ▼ ┌───────────────────────┐ ┌────────────────────────┐ │ Device Sub-CA G1 │ │ Server Sub-CA │ │ (현재 발급 중) │ │ (서버용) │ │ 10년 유효 │ │ │ └──────────┬────────────┘ └────────────┬───────────┘ │ 서명 (제조 라인에서) │ 서명 ▼ ▼ ┌──────────────────────┐ ┌──────────────────────┐ │ Buds Device Cert │ │ api.budsai.example │ │ - 디바이스마다 고유 │ │ - 서버 인증서 │ │ - 10년 유효 │ │ - 90일 자동 갱신 │ └──────────────────────┘ └──────────────────────┘

4.2 제조 라인 발급 시퀀스

  1. 버즈 ATE(자동 테스트 장비) 단계에서 SE에 키페어 생성 명령 — 개인키는 칩에서 안 나옴
  2. SE가 CSR(Certificate Signing Request) 출력 — 공개키 + 디바이스 시리얼
  3. 제조 라인 HSM이 Device Sub-CA로 CSR 서명 → 디바이스 인증서 생성
  4. 인증서를 SE의 별도 슬롯에 저장 (인증서는 공개 정보, RAM 노출 무방)
  5. SE Key Attestation — 키가 진짜 SE 안에서 생성됐는지 인증서로 증명 (Google AOSP 표준)
  6. 제조 데이터베이스에 디바이스 시리얼 ↔ 공개키 매핑 등록

4.3 폐기 메커니즘

  • CRL (Certificate Revocation List) — 매주 갱신, S3/CDN에 게시
  • OCSP Stapling — 서버가 핸드셰이크 시 OCSP 응답 동봉 → 버즈가 별도 OCSP 쿼리 안 해도 됨
  • 긴급 폐기 — 분실/도난 신고 시 시리얼을 즉시 CRL에 추가, 모든 mTLS 핸드셰이크 거부

5. Secure Element 깊이

5.1 SE란

Secure Element(SE)는 탬퍼 저항(tamper resistant) 마이크로컨트롤러로, 외부에서 키를 읽거나 추출할 수 없는 격리된 환경에서 암호 연산을 수행합니다. SIM 카드, 신용카드 IC칩, 폰의 Titan/SEP 모두 같은 카테고리.

5.2 후보 SE

제품제조사인증특징
SE050 / SE051 NXP CC EAL 6+ I²C, 풍부한 사례, 저전력
ATECC608B Microchip JIL High 저렴, 작은 패키지(8-pin)
OPTIGA Trust M Infineon CC EAL 6+ 풍부한 RSA/ECC
SoC 내장 SE (예: Samsung S3K) CC EAL 5+ 패키지 통합, BOM 절감

BudsAI는 SoC 내장 SE를 1순위, 외부 SE를 2순위로 검토 — BOM 비용 및 회로 면적 절감.

5.3 SE 인터페이스

// I²C 또는 SPI로 SE와 통신, APDU 프로토콜
// 키 생성
apdu_send(CMD_GENERATE_KEY, ECDSA_P256, slot=0x01);
// 응답: 공개키 65 바이트 (uncompressed P-256)

// CSR 생성 (또는 외부 CSR 빌더)
apdu_send(CMD_SIGN, slot=0x01, csr_tbs_data);
// 응답: ECDSA 서명

// TLS 핸드셰이크 중
apdu_send(CMD_SIGN, slot=0x01, certificate_verify_data);
// 응답: 서명 (mbedTLS opaque key API에 결과 반환)

5.4 측면 채널 공격 (Side Channel)

  • 전력 분석 (DPA) — SE는 마스킹/셔플링으로 방어
  • 전자기 방사 (EMA) — 패키지 차폐
  • 레이저/글리치 — 오류 주입 시 자가 락다운
  • 온도 공격 — 동작 온도 범위 밖에서 키 무효화

CC EAL 6+ 인증 SE는 위 모든 공격에 검증된 방어를 갖춥니다.

5.5 키 어테스테이션

SE 안에서 생성된 키임을 외부에 증명하려면 어테스테이션 인증서가 필요합니다. Google AOSP의 KeyMint 표준을 채택할 경우, 키 생성 시 SE 제조사 루트 인증서로 서명된 어테스테이션 체인을 함께 받아 서버에 제출 — "이 키는 진짜 SE 안에서 생성됐고 절대 추출 안 됨"을 증명.

6. JWT 깊이

6.1 왜 mTLS 위에 JWT를 또 쓰나

mTLS는 디바이스를 인증합니다. JWT는 그 디바이스에 묶인 사용자/세션을 인증합니다.

  • 한 디바이스가 여러 사용자에게 양도될 수 있음 (가족, 중고 거래)
  • 세션 만료/회수가 인증서 폐기보다 빨라야 함
  • 스코프/권한을 토큰에 담을 수 있음

6.2 JWT 구조

// JWT = base64url(header) . base64url(payload) . base64url(signature)

// Header
{
  "alg": "ES256",     // ECDSA + SHA-256
  "typ": "JWT",
  "kid": "k-2026-01"  // 서버 키 ID (로테이션용)
}

// Payload (claims)
{
  "iss": "https://auth.budsai.example",
  "sub": "user_8f3a92c1",        // 사용자 ID
  "aud": "api.budsai.example",
  "iat": 1762636800,
  "exp": 1762640400,             // 1시간 후 만료
  "jti": "tok_9e2f7b6a1",        // 토큰 고유 ID
  "device_id": "buds-3a7f2e91",  // 묶인 디바이스
  "scope": "audio:upload session:create",
  "tier": "free"                  // 비용 제어용
}

// Signature
ECDSA_sign(SHA256(header . "." . payload), server_private_key)

6.3 토큰 발급 흐름

  1. 최초 1회 — 사용자가 폰/웹에서 BudsAI 계정 가입
  2. 버즈 페어링 시 폰이 디바이스 시리얼 ↔ 계정 매핑 등록 API 호출
  3. 버즈가 mTLS로 /v1/token 호출 → 디바이스 인증서로 사용자 확인 → JWT 발급
  4. 버즈 RAM에만 보관, 만료 5분 전 자동 갱신
  5. 모든 후속 API 호출의 Authorization 헤더에 포함

6.4 토큰 회수

분실 신고 / 계정 탈퇴 / 비밀번호 변경 시 서버 측 deny-list에 jti 추가 — 만료 전이라도 거부. Deny-list는 redis로 운영, 토큰 만료 시간(보통 1시간) 후 자동 청소.

7. End-to-End 암호화 보장

7.1 무엇이 누구에게 보이는가

관찰자볼 수 있는 것볼 수 없는 것
Buds (자신) 모든 평문 —
호스트 (폰/노트북) L2/L3 헤더 (출발지/목적지 IP, 트래픽 양) TLS 페이로드 (오디오, 응답 텍스트)
ISP / 라우터 호스트 ↔ 서버 IP, SNI(api.budsai.example) TLS 페이로드
서버 (정당) 모든 평문 (필요해서) —
가짜 서버 (불법) 핸드셰이크 시 거부됨 아무 것도

7.2 BT 링크 자체 암호화

BT 페어링 시 LE Secure Connections(Bluetooth 4.2+)를 강제 — ECDH 키 교환 + AES-CCM 암호화. BT 레이어가 한 번 더 암호화하지만, 우리는 그것을 신뢰하지 않고 위에 TLS를 또 씌웁니다 (defense in depth).

7.3 메타데이터 최소화

  • 호스트는 TLS SNI를 통해 도메인만 볼 수 있음 → ESNI/ECH (Encrypted Client Hello) 활성화로 도메인까지 숨김
  • 패킷 길이 패딩 — 트래픽 분석 방어 (페이로드 크기로 콘텐츠 추측 차단)
  • 전송 타이밍 dithering — 짧은 랜덤 딜레이

8. 키 로테이션 / 폐기

8.1 로테이션 정책

대상주기방식
Root CA 25년 새 Root 사전 배포 후 cross-sign 점진 전환
Sub-CA 10년 Root로 새 Sub-CA 서명, 신규 디바이스부터 적용
Device Cert 10년 제조 시 발급, 만료 임박 시 OTA로 재발급
Server Cert 90일 ACME 자동 갱신
JWT 서명키 6개월 키 ID(kid)로 다중 활성 키 운영, 점진 전환
TLS 세션키 세션마다 ECDHE로 매번 새로 (Forward Secrecy)

8.2 침해 사고 대응

Sub-CA 침해 시 해당 Sub-CA의 모든 디바이스 인증서를 CRL에 추가 — 새 Sub-CA로 OTA 재발급. Root 침해는 25년 안에 1회도 없어야 하지만, 발생 시 비상 Root를 cross-sign으로 인계.

운영 노트 Root CA HSM은 에어갭(공기 차단) + 듀얼 컨트롤(2인 동시 인증) 환경에서만 깨어남. Sub-CA 발급도 키 의식(key ceremony)으로 진행 — 비디오 녹화, 다중 입회.
관련 문서 엔드포인트별 인증 흐름은 서버 API 페이지에서 다룹니다.
