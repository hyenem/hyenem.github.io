Slide 2 · Delegation Contract

위임할 때 주고받는 데이터는 무엇일까?

서버엔 AI 로직이 없으므로 실질 개발 범위는 "요청/응답 스키마 정의 + 응답 기반 라우팅". 아래는 각 필드의 의미.

▶ REQUEST · BudsAI → Galaxy AI 서버가 보내는 것
audio[3]
원본 오디오 3트랙 — internal(듣던 소리)·external(주변음)·voice(질문). 분석·요약 없는 날 것.
track_labels
각 트랙이 무엇인지 표시. 버즈가 캡처 때 붙인 메타라 서버가 판단한 게 아님.
timeline
세 트랙의 시간 정렬 정보. "발화가 어느 시점 소리를 가리키나"의 근거.
session_id
이 요청의 고유 ID. 나중에 응답을 맞춰 찾는 열쇠.
host_type
갤럭시폰 / Other hosts 구분. 출력 형태를 가름.
lang_hint
예상 언어 힌트(있으면). 전사·TTS 언어 결정에 참고.
분석 결과·요약 없음. 정렬만 끝낸 오디오 + 라벨만 보낸다.
◀ RESPONSE · Galaxy AI → BudsAI 서버가 받는 것
utterance_text
발화를 받아쓴 텍스트 (STT 결과). 예: "방금 이 노래 뭐야?"
needs_audio_ref
축1. 답하려면 듣던 소리를 봐야 하나? true=BudsAI task / false=일반.
action
축2. 무슨 동작인가(정해진 목록 중 하나). 예: music_identify, schedule_create.
target_track
참조할 트랙. internal / external / none. 음악이 카페 BGM이면 external.
needs_shazam
곡 식별이 필요한가? true면 서버가 Shazam 호출(Gemini엔 음악 DB 없음).
slots
동작에 필요한 값들. 예: 알람이면 {시간, 종류}.
confidence
분류 확신도. 낮으면 되묻기/fallback 트리거.
fallback_answer
분류 애매·핸들러 없을 때 대신 읽어줄 답변.
서버는 이 값만 보고 행동: needs_shazam→Shazam, action→핸들러 매핑.
읽는 법: 서버는 왼쪽(원본 오디오)을 보내고 오른쪽(구조화된 판단)을 돌려받는다. needs_audio_ref=오디오를 봐야 하나(축1), action=무엇을 할까(축2). action 목록: music_identify · schedule_create · sound_save · translate · summarize · call · smarthome · simple_qa(단순 질의응답·기본값). 미분류는 simple_qa + fallback_answer로 흡수한다.

프로세스별 기술 ① 정렬 · 위임 · 라우팅

"무엇을 듣고 있었나"와 "지금 묻는 게 그것과 관련 있나"를 푸는 단계. 각 기술이 맡는 역할을 먼저.

🧩세 트랙을 시간으로 맞춘다
PTS Multi-track Sync
기준 PTS대상 3-track
▸ STAGE 1
internal · external · user voice는 서로 다른 버퍼·시점에 캡처되므로 공통 PTS 타임라인에 재배열한다. 이로써 user voice가 internal/external audio의 정확히 어느 구간을 가리키는지 결정된다. HOW 각 프레임 PTS를 기준점으로 정렬 → 발화 직전 N초를 "참조 구간"으로 추출 → 후속 분석은 이 구간만 본다("방금 그 노래"의 그 노래 특정).
📦분석을 통째로 위임한다
Delegation Contract
SEND 원본 3트랙RECV JSON
▸ STAGE 2
서버는 STT·연관도·분류 모델을 갖지 않는다. 정렬만 끝낸 원본 3트랙 오디오 + 트랙 라벨을 그대로 Galaxy AI에 보내고, 분석은 전부 위임한다. 트랙 라벨조차 버즈가 캡처 시 붙인 메타라 서버는 추론하지 않는다. SEND {audio: [internal, external, voice], track_labels, session_id, lang_hint}  RECV 아래 분류 스키마(JSON).
🔗발화가 어느 소리를 가리키는지 푼다
Reference Resolution (Gemini 내부)
주체 Gemini범위 개발 밖
▸ STAGE 2 · 위임
연관도는 별도 점수가 아니라 지시 해소 문제다. 발화의 지시어("이","방금","지금")가 어느 트랙을 가리키는지 attention으로 찾는다. "노래"가 음악 구간과 정렬되면 그 트랙이 참조 대상, 어떤 트랙과도 정렬 안 되면 오디오 참조 불필요(일반 task). HOW 세 입력을 공통 잠재공간에 인코딩 → 발화 토큰↔오디오 구간 정렬 계산 → 연관도 판단과 task 분류가 한 추론에서 동시에 결정.
🧭2축으로 분류하고 라우팅한다
2-axis Classification + enum
축1 needs_audio_ref축2 action enum
▸ STAGE 2 → 3
분류는 직교하는 두 축이다. 축1(라우팅) needs_audio_ref → 오디오 참조 필요(BudsAI) / 불필요(일반). 축2(동작) action → music_identify·schedule_create·sound_save·translate·summarize·call·simple_qa(단순 질의응답). 서버는 이 enum만 보고 핸들러로 보낸다(판단 없음). HOW 고정 enum + escape hatch — 분류 애매하면 simple_qa + fallback_answer로 강등해 최소 TTS 답변 보장. Other hosts에선 앱 연동 action을 단순 질의응답으로 다운그레이드.

프로세스별 기술 ② 분석 · 추론 · 합성

3트랙을 각각 분석해 의도를 종합하고, 경로에 맞는 응답을 만든다.

🎵듣던 음악을 식별한다
Shazam API · Audio Fingerprinting
대상 internal + external매치 ~200ms
▸ STAGE 3 (음악 task)
음악은 internal audio(재생 중인 곡)뿐 아니라 external audio(카페·매장 BGM 등)에도 존재할 수 있다. Gemini는 음악 DB가 없어 곡 검색 정확도가 낮거나 불가하므로, task가 음악 관련이면 Shazam API를 직접 호출해 제목·아티스트·앨범 메타를 받아온 뒤, 그 결과를 Gemini에 위임해 Action Item을 만든다. HOW 음악 task 판정 → 해당 트랙(internal/external) 구간을 Shazam API로 조회 → {title, artist, album…} 회신 → Gemini가 이 메타로 답변·actions 종합.
🌐주변 환경음을 읽는다
Acoustic Event Detection + STT
대상 external audio
▸ STAGE 3
external audio 전용. 환경 성격(지하철·카페·거리)을 분류하고, 안내방송·대화 같은 음성이 있으면 STT로 텍스트화해 맥락에 더한다. 매장 BGM 등 음악이 섞여 있으면 Shazam API 식별 대상으로 함께 넘긴다. HOW AED가 비음성 사운드를 라벨링 → 음성 구간은 VAD로 분리 후 STT 적용 → 음악 감지 시 Shazam 호출 트리거 → 환경 라벨 + 전사 + 곡 메타를 함께 출력.
🗣사용자가 원하는 동작을 뽑는다
Intent Classification
대상 user voice출력 intent+params
▸ STAGE 3
user voice 전용. 전사된 발화에서 intent와 파라미터(시간·대상·장르 등)를 추출해 후속 핸들러가 쓸 구조로 만든다. HOW 의도 카탈로그(music·translate·summary·QA·schedule…)로 분류 → 슬롯 필링으로 params 추출 → Gemini 종합 입력으로 전달.
🤖맥락을 종합해 답과 액션을 만든다
Gemini / Galaxy AI (위임)
경로 Galaxyp50 ~0.8s
▸ STAGE 3
Galaxy 경로. 3트랙 산출물(환경/전사·intent)과 음악 task일 때 Shazam이 반환한 곡 메타를 Gemini가 종합해 자연어 답변과 우선순위 매긴 Action Item을 만든다. Gemini에는 음악 DB가 없으므로 곡 정보는 Shazam이 채워 주고 Gemini는 그 위에서 추론만 한다. HOW 멀티소스 컨텍스트(+곡 메타)를 프롬프트로 구성 → Gemini가 answer + 구조화된 actions(JSON) 생성 → Galaxy 생태계 핸들러에 매핑.
🧠Galaxy 없이도 답한다
Server 경량 LLM (대체)
경로 Other hosts불가 앱 연동
▸ STAGE 3
Other hosts 경로. Galaxy AI를 못 써 서버 내장 경량 LLM + FP DB로 검색 수준 질의응답만 처리한다. 일정 등록·저장 등 앱 연동 task는 불가. HOW FP 결과·STT 텍스트를 경량 LLM에 입력 → 간결한 답변 텍스트 생성(actions 미생성) → 4단계 TTS로 전달.
🔊답을 목소리로 들려준다
Neural TTS · VITS
코덱 Opus 24k첫음절 ~300ms
▸ STAGE 4
답변 텍스트를 자연스러운 음성으로 합성한다. 합성 위치가 경로별로 다른 게 핵심 — Galaxy는 폰에서, Other hosts는 서버에서 합성해 버즈로 보낸다. HOW 텍스트→음향특징→파형을 end-to-end 생성(VITS) → 스트리밍으로 첫 음절을 빠르게 → Opus 24kbps 인코딩 후 송신.

2
Now brief 화면 구성
transcript(텍스트화 없으면 공란 + 플레이 버튼으로 원본 재생) · answer_text · Action Item 카드(우선순위 순).
3
TTS 합성 → 버즈 재생
answer_text를 폰에서 직접 VITS로 합성·Opus 인코딩 후 버즈로 전송. (서버 아님)
4
action 실행 — 두 갈래
즉시 실행
명확한 명령(알람·전화·"방금 일정 등록")은 바로 핸들러 앱 호출 → 실행 후 "등록했어요" 확인 TTS.
카드 대기
음악 추천 등은 Now brief 카드로 띄우고 대기 → 사용자가 탭하면 그때 handler로 딥링크(YouTube Music·Calendar 등).
폰 = 사용자↔로컬 앱 라우터. 판단 없이 action_item의 {intent, params, handler}대로 안드로이드 인텐트/딥링크로 앱에 넘긴다.
💻 Other hosts 단순 통로
RECV ← TTS audio (Opus 24k)  // 서버가 합성 완료
1
서버가 TTS까지 완성해 전송
디바이스에 합성 능력(Galaxy AI)이 없으므로, 서버가 answer를 VITS 합성·Opus 인코딩한 음성 패킷을 만든다.
2
호스트는 passthrough만
받은 음성 패킷을 해석 없이 그대로 버즈로 흘려보낸다(BT PAN/BNEP 라우팅). E2E 암호화라 호스트는 내용도 못 봄.
3
버즈에서 재생
음성을 듣는 것이 전부. Now brief·카드·저장·앱 위임 모두 없음.
호스트 = 단순 통로. 앱 연동 task는 수행 불가 → "이 기능은 갤럭시 기기에서 가능합니다" 안내로 대체.
실행 분기: 명확한 명령은 즉시 실행, 추천처럼 선택지가 있는 건 카드로 띄워 사용자 선택을 대기한다. 갈림의 뿌리 = Galaxy AI 생태계 접근 여부 — 같은 "방금 이 노래 뭐야?"라도 Galaxy는 답변 + [같은 아티스트][플레이리스트][저장] 카드를, Other hosts는 음성만 돌려준다.
