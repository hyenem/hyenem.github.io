1. 전체 AI 파이프라인

[Session 도착] │ ▼ ┌────────────────────────────┐ │ Authenticator / Quota │ │ (mTLS + JWT 검증) │ └─────────────┬──────────────┘ ▼ ┌────────────────────────┐ │ Demux: Track A / B │ │ (Opus decode 병렬) │ └─────┬──────────────┬───┘ │ │ Track A │ │ Track B (질의 음성) ▼ ▼ ┌─────────────────┐ ┌──────────────────┐ │ Audio Analysis │ │ STT (Whisper) │ │ - VAD/loudness │ │ → query_text │ │ - 음악/말 분류 │ └────────┬─────────┘ │ - Fingerprint │ ▼ └────────┬────────┘ ┌──────────────────┐ │ │ Intent Classifier│ │ │ → intent + slots │ │ └────────┬─────────┘ │ │ └─────────┬──────────┘ ▼ ┌──────────────────────────────┐ │ Intent Router │ │ - song_id → Music DB │ │ - transcribe→ Track A STT │ │ - translate → MT model │ │ - define → 사전 + LLM │ │ - search → Web + LLM │ │ - summarize → LLM │ │ - classify → AudioClass │ │ - recommend → Reco engine │ └──────────────┬───────────────┘ ▼ ┌─────────────────┐ │ Response Builder│ │ (LLM, 자연어 만듦)│ └────────┬────────┘ ▼ ┌─────────────────┐ │ TTS (Neural) │ └────────┬────────┘ ▼ [Buds로 응답 스트리밍]

핵심 설계 원칙은 다음과 같습니다.

  • 병렬 처리 — Track A 분석과 Track B STT는 독립이라 동시 진행
  • 조기 시작 — Track B의 첫 ~500ms만 도착해도 STT 시작 (streaming STT)
  • 의도 라우팅 — 의도 분류 결과로 최소 모델만 호출 (LLM 호출 회피)
  • 응답 스트리밍 — TTS 첫 청크 즉시 전송, 전체 합성 대기 안 함

2. STT (Speech-to-Text) 깊이

2.1 후보 모델 비교

모델아키텍처다국어지연WER (한국어)
Whisper Large v3 Encoder-Decoder Transformer 99개 1-2s/30s ~7%
Whisper Medium 동일, 작은 크기 99개 ~0.5s/30s ~10%
Conformer-CTC CNN + Transformer + CTC 훈련 의존 스트리밍 가능 ~6% (한국어 특화 시)
Riva (NVIDIA) Conformer + RNNT 제공 스트리밍 ~8%
Google Cloud STT 독점 제공 스트리밍 ~5%

2.2 BudsAI의 선택

Track B(짧은 질의, ~5초)에는 Conformer-CTC 한국어/영어 멀티 자체 호스팅 모델. 스트리밍 가능 + 짧은 발화에 강함 + 비용 통제.

Track A에 STT가 필요한 의도(transcribe, summarize, define 등)는 Whisper Large v3 — 오프라인 배치 처리 가능, 다양한 환경음 강함.

2.3 Conformer 아키텍처 요약

Input: log-mel spectrogram (80 mels, 10ms hop) │ ▼ [Subsampling conv] (4× 다운샘플) │ ▼ [Conformer Block × 17] ┌─────────────────────────────────┐ │ FeedForward (½) │ │ Multi-Head Self-Attention │ │ Convolution Module (depth-wise) │ │ FeedForward (½) │ │ LayerNorm │ └─────────────────────────────────┘ │ ▼ [Linear projection → CTC vocab] │ ▼ CTC decoding (beam search, beam=10) │ ▼ Output: 문자/서브워드 시퀀스

2.4 스트리밍 디코딩

Conformer를 chunk-attention으로 설정 — 미래 정보를 제한적으로만 봐서 스트리밍 가능. Chunk size 640ms, look-ahead 80ms. 결과는 partial transcript로 매 chunk마다 갱신.

2.5 후처리

  • ITN (Inverse Text Normalization) — "이천이십육년" → "2026년"
  • 구두점 복원 — 별도 작은 BERT 모델
  • 대문자화 — 영어 부분
  • 이모티콘 제거 — Track A가 음악이면 가사 STT 시 강조 표현 제거

2.6 한국어 특화 처리

  • 외래어 음역 정규화 (e.g. "쿠앙" → "Kuang" or 그대로)
  • 존댓말 어미 유지 — "였습니다" 같은 형태 보존
  • 코드 스위칭 — "방금 quintessential 뜻" 같은 한영 혼합 문장 인식

3. Intent Classification 깊이

3.1 의도 체계

BudsAI는 8개 최상위 의도 + 각 의도별 slot을 정의합니다.

Intent의미주요 slot핸들러
song_id곡 식별—Audio Fingerprint
transcribe받아쓰기language, rangeTrack A STT
summarize요약length, styleSTT + LLM
define단어 뜻target_word, langSTT + 사전 API
translate번역src_lang, tgt_langSTT + MT 모델
classify환경음 분류—AudioCLIP
search외부 검색querySTT + Search + LLM
recommend추천seed_typeReco 시스템

3.2 분류 모델 비교

접근정확도지연유연성
키워드 매칭 (정규식) ~75% 1ms 매우 낮음
경량 BERT (DistilBERT) ~92% 30ms 중간 (재학습 필요)
SetFit (few-shot) ~90% 20ms 높음 (적은 데이터로 추가)
LLM zero-shot ~95% 150ms 매우 높음 (프롬프트만)

3.3 캐스케이드 라우팅

지연 예산을 지키기 위해 캐스케이드로 동작.

  1. 레벨 1 — 키워드 게이트 : "이 노래 뭐야" / "번역해줘" 등 명백한 케이스를 5ms에 라우팅
  2. 레벨 2 — DistilBERT : 게이트 실패 시 30ms 안에 의도 분류
  3. 레벨 3 — LLM 보강 : DistilBERT 신뢰도 < 0.7일 때만 LLM 호출 (전체의 ~5%)

평균 의도 분류 지연 = 약 12ms.

3.4 slot 추출

Slot은 BIO-tagging으로 추출. 예: "한국어로 번역해줘" → tgt_lang=ko. 한국어 BERT의 토큰 단위 NER 헤드로 처리.

3.5 학습 데이터

  • 자체 수집 발화: 의도당 ~500 표본
  • 합성 데이터 (LLM으로 paraphrase): 의도당 ~2000 표본
  • 실제 사용 로그 (사용자 동의 하): 매주 능동학습 사이클로 추가

4. Audio Fingerprinting (음악 식별) 깊이

4.1 기본 원리 — Wang 2003 알고리즘

Shazam의 핵심 논문 (Wang 2003)이 정한 패러다임. 오디오의 시간-주파수 도메인에서 peak point를 뽑아 그 페어로 해시를 만듭니다.

1) 오디오 → STFT (Short-Time Fourier Transform) → 스펙트로그램 2) 스펙트로그램에서 local maxima (peak) 추출 → 시간/주파수 좌표 (t, f) 3) Peak 페어로 fingerprint 해시 생성: hash = (f1, f2, Δt) 이 hash는 anchor=(t1, f1) → target=(t2, f2)의 관계 4) 데이터베이스 형태: hash → [(song_id, t1), (song_id, t1), ...] 5) 쿼리 시: 쿼리 hash들을 DB에 lookup 매칭된 (song_id, song_t - query_t) offset 히스토그램 만들기 특정 offset에 강하게 집중된 song_id가 정답

4.2 왜 Peak Pair 인가

  • 잡음 강건 — 절대값이 아닌 상대적 peak 위치만 사용
  • 시간 시프트 무관 — 곡 어디서 들었어도 매칭
  • 저장 효율 — 곡 1초당 ~10-20 hash만 필요
  • 쿼리 효율 — DB는 단순 해시 lookup

4.3 BudsAI 구현 디테일

// 1. PCM (Track A) → resample to 16kHz mono
// 2. STFT
//    window = 1024 (Hann)
//    hop    = 64    (overlap 94%, 시간 해상도 4ms)
//    nfft   = 1024
// 3. Power spectrogram log scale
// 4. Local maxima detection
//    구역 검사: 21 (freq) × 11 (time)
//    threshold: power > avg + 2*std
// 5. Anchor selection
//    1초당 평균 10 anchors
// 6. Target zone
//    anchor 기준 +50 frame (200ms) 내 가까운 3 peaks와 페어링
// 7. Hash
//    h = (f1 :: f2 :: Δt) — 32-bit fingerprint
// 8. DB lookup
//    Redis cluster, hash → posting list

4.4 매칭 점수 산정

쿼리에서 N개 해시를 뽑아 DB에서 매칭된 곡별로 (song_t - query_t) 히스토그램. 가장 높은 bin의 점수가 임계값 초과 + 2등과의 마진이 충분하면 confident match.

4.5 라이브러리 / 데이터셋

  • 음악 카탈로그 — Melon/지니 등 라이센스 계약, 1억곡+ fingerprint DB
  • 오픈소스 비교 — Dejavu, Chromaprint(MusicBrainz), Olaf
  • 저작권 메타 — ISRC + 아티스트 + 앨범 + 발매일

4.6 단점 / 한계

  • 커버곡/리믹스는 다른 곡으로 인식 (정확히 같은 마스터만 매칭)
  • 매우 시끄러운 환경(SNR < -10dB)에서 정확도 저하
  • 10초 미만의 매우 짧은 샘플은 false positive 증가
  • 최근 발매 곡은 DB 인덱싱 시간차로 인해 일부 미인식

4.7 환경음 분류와의 분기

Track A를 먼저 "음악인가 환경음인가 말소리인가" 분류 후, 음악일 때만 fingerprint. 분류기는 YAMNet (Google) 또는 자체 PANNs 모델 사용 — 1초 안에 521 클래스 분류.

5. TTS (Text-to-Speech) 깊이

5.1 Neural TTS 시대

2018년 이전 concatenative TTS는 부자연스러웠으나, neural TTS는 사람 목소리와 구별 어려운 수준에 도달했습니다. BudsAI는 VITS / Bark / XTTS 계열 neural TTS 활용.

5.2 후보 모델

모델아키텍처다국어RTF품질
VITS VAE + Flow + GAN 훈련별 0.05 높음
XTTS-v2 GPT + Tortoise 16개 0.3 매우 높음 (보이스 클로닝)
Bark GPT 계열 여러 1.0+ 표현력 매우 높음
StyleTTS 2 Diffusion 훈련별 0.2 매우 높음
Google WaveNet 독점 여러 실시간 매우 높음

RTF (Real Time Factor) = 합성 시간 / 출력 길이. 0.1 이하면 실시간 가능.

5.3 VITS 아키텍처 요약

Text → Phonemizer → Phoneme sequence │ ▼ [Text Encoder Transformer] │ ▼ [Stochastic Duration Predictor] ← 음소별 길이 결정 │ ▼ [Normalizing Flow] ← Latent space 인코딩 │ ▼ [HiFi-GAN Vocoder] ← 파형 합성 │ ▼ 24kHz audio waveform

5.4 스트리밍 합성

VITS 자체는 비스트리밍이지만, 문장 경계 또는 구두점에서 chunk 분할 후 병렬 합성으로 첫 청크를 빠르게 전송. 평균 첫 음 출력 지연 ~200ms.

5.5 음성 캐릭터 선택

  • 한국어: 여성 차분, 남성 활기, 어린이, 노년 — 4가지 디폴트
  • 영어: 미국 표준, 영국, 호주
  • 사용자 보이스 클로닝(옵션, 30초 샘플) — XTTS-v2 경로

5.6 응답 출력 형식

합성 결과는 24kHz 16-bit PCM → 다시 Opus 인코딩 → BudsAI 자체 패킷으로 스트리밍.

6. LLM 라우팅 & 컨텍스트

6.1 LLM은 언제 호출되나

모든 의도가 LLM을 부르는 건 아닙니다. 비용/지연 때문에 필요한 경우만 호출.

IntentLLM 호출?이유
song_id❌fingerprint + DB lookup만
transcribe❌STT 결과 그대로
summarize✅LLM이 유일한 솔루션
define옵션사전 1차, 의미 모호 시 LLM 보강
translate전용 MT 모델 1차, 어려운 케이스만 LLM비용
classify❌AudioCLIP만
search✅검색 결과 통합 + 답변 작문
recommend옵션Reco 1차, 이유 설명 시 LLM

6.2 LLM 모델 선택 (티어드)

  • 경량 (자체 호스팅 Llama 3.1 8B / Qwen2.5 7B) — 단순 요약·답변, 응답 1초 이내
  • 중량 (Claude Sonnet / GPT-4o-mini API) — 복잡한 추론, 응답 2-3초
  • 대형 (Claude Opus / GPT-4o API) — 정말 어려운 케이스, 응답 3-5초

의도 분류 결과 + 사용자 티어 + 신뢰도로 라우터가 모델 선택.

6.4 세션 컨텍스트 유지

PrevSessionID가 있으면 이전 세션의 요약을 짧게 포함 → "근데 이 가수 다른 곡도 추천해줘" 같은 후속 질문 처리. 전체 이전 대화를 다 넣지 않고 LLM이 만든 1-2문장 요약만 사용 (컨텍스트 비용 제어).

6.5 안전 / 환각 방지

  • 출처 강제 — search intent는 검색 결과 인용 외 답변 금지
  • 거절 케이스 — 의료/법률/혐오 질문은 정중히 거절
  • 저작권 — 가사/책 본문은 부분만 인용, 전체 재생산 금지
  • 개인정보 — Track A에 실명/주민번호가 있어도 응답에 노출 안 함

7.1 최악 케이스

대형 LLM 호출(search intent + Opus 4 API) 시 +1.5초. 사용자에게 "잠시만요" Earcon 후 결과 도착 시 응답 — 진행 표시.

7.2 캐싱 전략

  • 같은 곡에 대한 같은 질문은 LLM 응답 캐시 (24h)
  • 자주 묻는 단어 정의는 사전 결과 캐시 (영구)
  • STT 결과는 캐시 안 함 (개인정보)
