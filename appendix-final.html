"실제로 쓸 수 있나"의 답: 대부분의 호스트에선 그렇다. Android의 "Bluetooth 테더링" 토글이 정확히 NAP를 띄우고, iPhone Personal Hotspot의 BT 옵션, Windows·iPadOS·Linux도 모두 동작. 실측에서 일반 웹·메시지·SSH·480p 영상까지 무리 없음. 예외는 macOS Monterey 이후 — Apple이 BT PAN을 제거해서 맥북은 더 이상 안 됨 (USB·Wi-Fi 핫스팟으로 대체).
⚠ 현실 체크 — 두 가지 사실: (1) macOS는 Monterey(2021)부터 BT 테더링을 제거했다. Sonoma·Sequoia·Tahoe 모두 인터페이스 목록에서 Bluetooth PAN 항목 자체가 사라졌다. 맥북에선 USB·Wi-Fi 핫스팟만 가능.   (2) Galaxy Buds의 공식 프로파일은 A2DP·AVRCP·HFP만이라 현재 펌웨어로는 PAN이 불가능 — 다만 이는 하드웨어 한계가 아니라 소프트웨어 결정이다. Samsung은 Buds2에 LE Audio Auracast를 펌웨어 업데이트로 추가한 전례가 있고, lwIP(~40 KB ROM) + BNEP(~10 KB) + mbedTLS(~80 KB)는 Buds3 Pro급 SoC의 플래시·SRAM 예산 안에 들어간다. 즉 "버즈가 직접 BNEP+TLS로 인터넷에 붙는다"는 펌웨어 업데이트로 도달 가능한 옵션이지, 칩을 바꿔야 하는 문제가 아니다.

/* ───── DUAL RING BUFFER LAYOUT ───── */ struct audio_dual_ring { /* Buffer A : 외부 환경음 30s 룩백 @ 16kbps SILK ─── 60 KB */ uint8_t A_buf[60 * 1024]; uint16_t A_slot_len[1500]; /* 20ms × 1500 = 30s */ uint32_t A_slot_pts[1500]; /* PTS in ms */ uint16_t A_head, A_tail; opus_encoder_t *enc_A; /* MODE_VOIP, DTX off */ /* Buffer B : 사용자 질문 5s @ 24kbps Hybrid ─── 16 KB */ uint8_t B_buf[16 * 1024]; uint16_t B_slot_len[250]; uint16_t B_head, B_tail; opus_encoder_t *enc_B; /* MODE_VOIP, DTX on */ vad_state_t *vad_B; /* 종료 감지 */ uint32_t shared_pts_origin; /* 두 트랙 시간정렬 */ }; /* TOTAL ≈ 80 KB */
/* Trigger flow */ 1. 상시: A 회전 (DMA → enc_A → A_buf, 1500 슬롯 wrap) 2. Wake/tap → A_snapshot = A.write_offset (동결) 3. enc_B 시작, B_buf에 사용자 음성 기록 4. VAD가 500ms 침묵 / 5s 한계 감지 → enc_B close 5. Session msg = A_snapshot ‖ B_total → host 전송 6. B reset · A는 계속 회전 (끊김 없음)

SILK

선형예측

음성 특화. LPC + LTP + 노이즈 셰이핑. 6–32 kbps 영역 SOTA.

CELT

MDCT + range

음악 특화. MDCT 변환 + 산술 부호화. 32–510 kbps, 48 kHz fullband.

Hybrid mode

SILK+CELT

저역은 SILK, 고역은 CELT. SWB·FB 음성 + 약한 음악에 사용.

CPU 비용

Cortex-M33

SILK 16 kbps enc @ 200 MHz ≈ 15%. 두 인스턴스 동시도 30% 미만. 디코더는 1/5.

메모리 결론: 30초 환경음(60 KB) + 5초 질문(16 KB) + 메타 ≈ ~80 KB. Buds3 Pro급 SoC의 SRAM(통상 512 KB – 1 MB) + 외부 PSRAM(수 MB)에 비해 압도적 여유. ANC는 별도 DSP 코어에서 돌고, Opus enc는 두 인스턴스 모두 메인 Cortex-M에서 충분히 처리. 메모리는 이 설계의 병목이 아니다.

BudsAI 선택: 1차 구현은 WebRTC VAD mode 3(검증된 GMM, 5 KB, 0.1 ms / 30 ms 프레임)으로 시작 — 펌웨어 풋프린트를 최소화. 정확도가 부족하면 Silero quantized(INT8, ~600 KB)로 단계 업그레이드. wake-word는 별도 KWS 모델이 담당하고, VAD는 오직 "질문이 끝났는가"만 본다.

왜 VAD를 트리거에 쓰지 않는가: 트리거에 VAD를 쓰면 사용자가 말하지 않을 때도 끊임없이 누군가의 음성을 캡처하게 됨 → 프라이버시·전력 모두 손해. BudsAI는 명시적 트리거(롱프레스 또는 키프레이즈)로 시작하고, VAD는 끝맺음 자동화에만 관여. 사용자는 "끝" 버튼을 누를 필요가 없다.

왜 ANC와 AI가 충돌하지 않는가설명
① 생산자가 단 하나 (DMA)RAW에 쓰는 주체가 유일 → 일관된 view
② 소비자는 모두 read-only둘 다 데이터 변형 안 함 → 데이터 레이스 불가
③ read_ptr가 각자 독립ANC의 latest와 AI의 frame_start가 서로 무관
④ 타임 스케일 분리ANC µs vs AI ms → 캐시·버스 경합 사실상 zero
⑤ DMA-coherent MPU region캐시 stale 문제 차단 (Cortex-M7 한정 필요)
⑥ 별도 마이크 경로외부 mic ≠ 내부 mic → enc_B는 다른 DMA zone
핵심 보장: "ANC가 실시간으로 외부 소음을 빼고 있는 그 순간에도, BudsAI는 동일한 외부음을 독립적으로 압축·전송할 수 있다." 두 경로는 같은 DMA가 쓴 한 줄의 메모리 위에 read-only fan-out으로 붙어 있으므로 물리적으로 충돌이 불가능. Apple AirPods의 Voice Isolation, Bose QC의 Conversation 모드도 동일한 SPMC 패턴 위에 구현되어 있다.
