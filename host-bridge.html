05 · UNIVERSAL HOST BRIDGE

범용 호스트 브릿지

앱 설치 없이 폰·노트북·MP3·TV·차량 등 BT+인터넷이 되는 모든 기기를 통해 동작. OS가 이미 가지고 있는 표준 BT 프로파일을 활용.

핵심 통찰 모바일 OS에는 "BT 드라이버 자동 설치" 같은 개념이 없습니다. 대신 OS들은 이미 표준 Bluetooth 프로파일을 빌드에 포함하고 있습니다. 우리가 이미 모두에 퍼져 있는 표준만 쓰면, 사용자는 아무 것도 설치할 필요가 없습니다.

1. 왜 어려운가

  • 모바일 OS(iOS/Android)는 보안상 임의 드라이버 설치를 허용하지 않음
  • BT 표준은 "프로파일" 단위로 OS 빌드에 포함됨 — 후추가 불가
  • 벤더(Apple/Google/Samsung)가 이미 구현한 프로파일만 무설치로 사용 가능

그래서 답은 "새 드라이버를 어떻게 설치할까"가 아니라 "이미 모두가 가진 프로파일 중 인터넷 브릿지에 쓸 수 있는 게 뭐냐"입니다.

2. 정답: Bluetooth PAN (Personal Area Network)

Bluetooth 표준에 PAN 프로파일이 있습니다. BNEP(BT Network Encapsulation Protocol)로 이더넷 프레임을 BT 위에 캡슐화해서, BT 페어로 IP 네트워크를 만듭니다.

2.1 역할

  • NAP (Network Access Point): 인터넷 게이트웨이 역할 — 폰/노트북/TV 등 host
  • PANU (PAN User): 게이트웨이를 통해 접속하는 클라이언트 — 버즈
  • 모든 데스크톱·대부분 모바일 OS가 NAP 역할을 OS 레벨에 내장

2.2 무설치 동작 방식

  1. 버즈가 BT 페어링 시 PAN 프로파일을 광고 (advertised services에 NAP 클라이언트 표기)
  2. 호스트 OS가 "BT 테더링" 요청으로 인식 — 사용자가 토글 한 번 (또는 자동 승인 정책)
  3. OS가 BNEP 채널 오픈, 버즈에 IP 주소 할당 (DHCP)
  4. 버즈 펌웨어 내 TCP/IP 스택이 즉시 동작 — DNS → TLS → HTTPS 직접
  5. 호스트는 NAT/라우터 역할만, 페이로드 안 들여다봄
중요 사용자 액션은 BT 테더링 토글 한 번 (또는 OS 정책에 따라 자동 승인). 앱 설치 0, 추가 페어링 0, 별도 계정 0.

3. USB CDC-NCM과의 유사성

USB 세계에서는 CDC-NCM(Communications Device Class - Network Control Model)이 같은 역할을 합니다. USB 동글을 꽂으면 모든 OS가 자동으로 "네트워크 어댑터"로 인식해 추가 설치 없이 인터넷 공유.

관점USB CDC-NCMBluetooth PAN
버스USBBluetooth Classic (또는 BLE에서 IPSP)
OS 레벨 지원모든 메이저 OS 빌트인모든 데스크톱·대부분 모바일 빌트인
설치 필요없음없음
역할USB 디바이스가 네트워크 어댑터처럼 보임BT 디바이스가 네트워크 클라이언트로 들어감
사용처USB 모뎀, 스마트폰 테더링BT 테더링, IoT 게이트웨이

본질적으로 "PAN은 BT의 CDC-NCM"입니다.

4. PAN 위에서의 아키텍처

┌─────────────────┐ ┌──────────────────┐ ┌──────────┐ │ Buds │ │ Host │ │ Server │ │ (PANU client) │ │ (NAP access pt) │ │ │ │ │ │ │ │ │ │ ┌────────────┐ │ BNEP │ ┌──────────────┐ │ IP │ │ │ │ App: HTTPS │ │ over │ │ NAT / Router │ │ (Wi-Fi │ │ │ │ Session │ │ L2CAP │ │ │ │ /LTE │ │ │ │ Message │◄──┼─────────┼─┤ │◄─┼─/etc)──►│ │ │ └────────────┘ │ │ └──────────────┘ │ │ │ │ TLS endpoint │ │ 페이로드는 봄 X │ │ TLS endpt│ │ TCP/IP stack │ │ (그냥 IP 라우팅) │ │ │ │ BNEP │ │ 표준 OS 기능 │ │ │ └─────────────────┘ └──────────────────┘ └──────────┘ ▲ ▲ │ │ └─────────────── End-to-End TLS (mTLS) ─────────────────┘

호스트는 IP 라우터일 뿐. 페이로드는 버즈 ↔ 서버 사이 mTLS로 암호화 — 호스트는 못 봄.

4.1 IP 레벨에서 보이는 것

  • 버즈는 일반 IoT 디바이스처럼 IP를 받고 인터넷에 나감 (예: 192.168.44.7)
  • DNS도 호스트가 표준 DHCP로 제공한 리졸버 사용
  • TLS 핸드셰이크는 버즈가 직접 수행 — 호스트는 암호문 패킷만 봄

5.1 BLE 기반 대안 (IPSP / 6LoWPAN-BLE)

PAN은 Classic Bluetooth이라 전력 소모가 큰 편. BLE 기반 IPSP(Internet Protocol Support Profile)가 저전력 대안이지만 OS 채택이 미진합니다(특히 iOS). 향후 OS 지원이 늘면 옵션으로.

6. PAN 안 되는 곳을 위한 대안

주로 iOS와 일부 dumb 기기를 위한 fallback.

6.1 Web Bluetooth 브릿지 페이지

버즈에 인쇄된 QR 코드를 폰 카메라로 스캔 → 웹페이지 한 탭이 열리고 브라우저가 BT 페어링 → JS가 BT ↔ 서버 데이터 포워딩.

  • 지원: Chrome / Edge (Win/Mac/Linux/Android/ChromeOS)
  • 미지원: iOS Safari (Web BT 미지원)
  • 장점: 앱 0, 계정 0, 탭 닫으면 끝
  • 단점: 탭이 열려 있어야 함

6.2 Generic BudsBridge App (오픈 스펙)

이전 안 그대로. iOS처럼 PAN 막힌 곳에서 fallback. 어떤 벤더의 버즈도 같은 앱 재사용.

6.3 HFP/PSTN 콜 fallback (극단)

버즈가 HFP로 폰을 통해 전용 전화번호에 다이얼 → 서버 SIP 게이트웨이가 응답 → 음성 통화 자체를 데이터 채널처럼 사용. 진짜 모든 폰에서 작동하지만 비용·지연·품질 문제로 비상용.

6.4 NFC/QR로 임시 토큰 받는 방식

인터넷 없는 환경에서 사용자가 QR로 임시 응답 토큰을 받아 외부 기기에서 결과 확인. 보조 시나리오.

7. eSIM in Buds — 호스트가 필요 없는 경로

가장 자유로운 옵션: 버즈 자체에 eSIM 또는 NB-IoT/LTE-M 모듈을 내장.

✅ 장점

호스트 0, 어디서나 동작. 폰 두고 산책가도, 노트북 없어도, MP3가 인터넷 안 되어도 그냥 됨.

❌ 단점

모듈/안테나 추가 → 부피·배터리 부담. 데이터 플랜·요금 발생. 통신 인증/규제 부담.

7.1 적용 시나리오

  • 프리미엄 모델만: Galaxy Watch LTE처럼 일부 SKU에만 탑재
  • 저전력 IoT 네트워크: LTE-M / NB-IoT (대역폭 작음, 배터리 좋음) — 데이터량이 적으면 OK
  • 요금: 통합 데이터 플랜 / Galaxy LTE 패밀리 플랜에 묶음

7.2 페이로드 최적화

eSIM 비용 줄이려면 데이터를 더 압축. 30초 Track A를 Opus 16kbps로 다운샘플 → ~60KB. 답변 TTS도 짧게 → 한 세션 ~100KB. 한 달 100세션 = 10MB.

8. 단계별 추천 전략

현실적으로 한 번에 한 길로는 충분하지 않으니 계층 구성:

┌─ Tier 1 (default) ────────────────────────────────────────┐ │ Bluetooth PAN (NAP) │ │ → 거의 모든 데스크톱·Android·임베디드 Linux 호스트 │ │ → 사용자 액션: BT 테더링 토글 한 번 (자주 자동 정책 가능) │ └────────────────────────────────────────────────────────────┘ │ 안 되면 ▼ ┌─ Tier 2 (iOS 등) ──────────────────────────────────────────┐ │ Web Bluetooth 브릿지 (브라우저 탭) │ │ → 폰 카메라로 QR 스캔 → 한 탭 │ │ → 앱 설치 0 │ └────────────────────────────────────────────────────────────┘ │ 안 되면 (iOS Safari 등) ▼ ┌─ Tier 3 (호환성 fallback) ─────────────────────────────────┐ │ Generic BudsBridge 앱 (오픈 스펙, 모든 벤더 공용) │ │ → 앱 1개 설치 후 어떤 호환 버즈에도 동작 │ └────────────────────────────────────────────────────────────┘ │ 호스트 자체 없음 ▼ ┌─ Tier 4 (프리미엄) ────────────────────────────────────────┐ │ eSIM in Buds │ │ → 호스트 필요 없음, 완전 독립 │ │ → 추가 비용 / 일부 SKU 한정 │ └────────────────────────────────────────────────────────────┘

버즈는 4개 path를 모두 알고 있고, 가능한 것 중 가장 효율적인 걸 자동 선택:

  1. BT 페어 직후 PAN 서비스 디스커버리 시도
  2. 실패 시 PSM 기반 GATT bridge 시도 (Web BT 또는 BudsBridge 앱)
  3. 모두 실패 시 eSIM 모듈 활성 (있을 때)
  4. 아무것도 안 되면 "인터넷 안 됨" 안내음

9. 펌웨어 비용

버즈가 PAN 클라이언트가 되려면 펌웨어 추가 부담이 있음:

모듈대략 사이즈비고
BNEP (PAN encap)~8 KBBT 스택 확장
lwIP (경량 TCP/IP)~30~60 KB이미 채택된 임베디드 표준
mbedTLS / WolfSSL (TLS 1.3)~80~120 KB핵심 — SE와 연동
DNS / DHCP 클라이언트~10 KB표준 라이브러리
HTTP/2 또는 HTTP/1.1 클라이언트~20~40 KBWebSocket 필요 시 +α
합계~150~250 KB최신 BT SoC 플래시로 수용 가능

9.1 전력 영향

  • BT Classic PAN: 송수신 시 ~20~30 mA 추가 (BLE보다 큼)
  • 완화: 평소엔 휴면, 트리거 시에만 active
  • 한 세션당 ~2초 active → 무시할 수준 (음악 재생보다 적음)
