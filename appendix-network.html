1. Bluetooth 스택 전체 구조

Bluetooth는 Classic(BR/EDR)과 LE(Low Energy) 두 가지 무선 모드를 가지며, 그 위에 여러 "프로파일"이 표준화되어 있습니다.

┌─────────────────── Application Profiles ────────────────────┐ │ A2DP HFP AVRCP HID GATT PAN(NAP/PANU) │ │ (오디오) (전화) (제어) (HID) (BLE 표준) (네트워크) │ └──────────┬──────────────┬──────────────┬──────────────┬──────┘ │ │ │ │ L2CAP RFCOMM BNEP ATT (다중 채널) (시리얼) (네트워크) (속성) │ │ │ │ ─────────────────── HCI (Host Controller Interface) ────────── │ ┌─────────────────┴──────────────────┐ │ BT Controller (Radio + Baseband) │ │ - Classic BR/EDR / LE PHY │ └────────────────────────────────────┘

1.1 BudsAI가 쓰는 프로파일

  • A2DP : 호스트 → 버즈 오디오 스트리밍 (기존 기능, 사용자 음악 재생)
  • AVRCP : 트랙 컨트롤 메타데이터 (제어용)
  • PAN (NAP/PANU) : 핵심 — 인터넷 브릿지
  • GATT : (선택) Galaxy 컴패니언 앱과의 메타 채널

2. PAN (Personal Area Network) 프로파일

2.1 표준 정의

Bluetooth SIG가 정의한 PAN 프로파일은 BT 디바이스를 이더넷 네트워크 노드로 만듭니다. IEEE 802.3 이더넷 프레임을 BNEP로 캡슐화해 BT 위에서 IP 라우팅을 가능하게 합니다.

2.2 3가지 역할

역할약어기능BudsAI에서
Network Access Point NAP 외부 네트워크(인터넷)로 게이트웨이 호스트(폰/노트북/TV/차량)
Group Ad-hoc Network GN BT 디바이스끼리만의 LAN 사용 안 함
PAN User PANU NAP/GN을 통해 접속하는 클라이언트 버즈

2.3 페어링 & 연결 시퀀스

  1. 버즈가 SDP(Service Discovery Protocol)로 NAP 서비스 광고 — UUID = 0x1116 (NAP)
  2. 호스트 OS가 "BT 테더링 요청" UI 표시 (또는 정책에 따라 자동 승인)
  3. 사용자 토글 ON → 호스트가 BT L2CAP 채널 오픈, PSM = 0x000F (BNEP)
  4. BNEP 핸드셰이크 — 사용자/네트워크 타입 협상 (IPv4 = 0x0800)
  5. 호스트가 DHCP 서버 역할 시작 — 버즈에 192.168.44.x 같은 사설 IP 할당
  6. 버즈가 ARP로 호스트(게이트웨이) MAC 학습 → IP 라우팅 시작

2.4 데이터 율

  • BT Classic 5.0 EDR : 이론 ~2.1 Mbps, 실효 ~1.4 Mbps
  • BT 5.0 LE 2M PHY : 이론 2 Mbps, 실효 ~1.4 Mbps
  • BudsAI 페이로드 : 30s Opus 음악 트랙 ~150KB → 약 0.9초 전송
  • 충돌 : A2DP 활성 시 대역폭 공유 — A2DP가 우선되므로 PAN 전송이 잠시 슬로우다운
A2DP와의 상호 영향 호스트 → 버즈 A2DP 스트림이 동작 중일 때 PAN 업로드는 가용 대역 중 ~30%만 사용 가능. 실측 30s 페이로드 전송 시간 약 2.5초 발생 → 의도 분류 응답 시간 SLA에 반영.

3. BNEP (Bluetooth Network Encapsulation Protocol) 깊이

3.1 역할

BNEP는 L2CAP 위에서 동작하며, 이더넷 프레임을 BT 패킷으로 캡슐화합니다. OSI 모델로 보면 데이터 링크 계층(L2)에 해당.

3.2 패킷 포맷

┌─────────────┬─────────────┬─────────────────────────────────┐ │ BNEP Header │ Ethernet │ IP Payload │ │ (1–14 byte) │ Addresses │ (TCP/UDP/...) │ └─────────────┴─────────────┴─────────────────────────────────┘ BNEP Header types: 0x00 : GENERAL_ETHERNET (full 6+6+2 byte addresses) 0x01 : COMPRESSED_ETHERNET (no addresses — 이미 알고 있음) 0x02 : COMPRESSED_SRC_ONLY 0x03 : COMPRESSED_DST_ONLY 0x04 : CONTROL (handshake) Type 0x01 사용 시 14 바이트 절약 — 매 프레임마다 효율 ↑

3.3 핸드셰이크

L2CAP_Connect (PSM=0x000F)
  ↓
BNEP_SETUP_CONNECTION_REQUEST
  Destination UUID: 0x1116 (NAP)
  Source UUID:      0x1115 (PANU)
  ↓
BNEP_SETUP_CONNECTION_RESPONSE
  Status: 0x00 (Operation Successful)
  ↓
[ data frames flow ]

3.4 필터링

BNEP는 두 가지 필터를 협상할 수 있습니다.

  • Network Type Filter — IPv4 0x0800, IPv6 0x86DD, ARP 0x0806 등만 통과
  • Multicast Address Filter — 특정 멀티캐스트 그룹만 통과

BudsAI는 IPv4 + ARP만 화이트리스트해서 호스트 LAN의 노이즈 트래픽이 버즈 펌웨어로 안 들어오게 합니다.

3.5 MTU 협상

BNEP 표준 MTU는 1691 바이트(이더넷 MTU 1500 + BNEP 헤더 여유). BudsAI는 BT L2CAP MTU를 1024로 협상 — RAM 제약 때문에 더 작은 버퍼로 동작. IP 레이어에서 fragment 처리.

4. 임베디드 TCP/IP 스택

4.1 왜 펌웨어에 TCP/IP가 있어야 하나

버즈가 mTLS 종단점이 되려면, BT 위에 IP 패킷을 직접 만들고 받아야 합니다. 호스트는 단순 라우터 역할만 하므로 TCP 연결 자체는 버즈 펌웨어 안에서 끝납니다. 이를 위해 임베디드 TCP/IP 스택이 필요합니다.

4.2 후보 비교

스택라이센스코드 크기RAMBudsAI 적합도
lwIP BSD ~40 KB ~25 KB ★★★ 채택
uIP BSD ~6 KB ~2 KB TLS 핸들 어려움
FreeRTOS+TCP MIT ~50 KB ~30 KB FreeRTOS 종속
NXP NetX Duo 독점 (현재 Azure RTOS 일부 무료) ~80 KB ~40 KB RTOS 매칭 시 고려

lwIP를 채택한 이유 : 가장 널리 검증됨, TLS 라이브러리(mbedTLS) 통합 사례 풍부, RAM 제약(64–128 KB) 안에서 동작.

4.3 lwIP 설정

// lwipopts.h
#define LWIP_TCP                1
#define LWIP_UDP                1   // DNS 위함
#define LWIP_DHCP               1
#define LWIP_DNS                1
#define LWIP_ARP                1
#define LWIP_NETIF_API          1

#define MEM_SIZE                32768   // heap
#define TCP_MSS                 1024
#define TCP_WND                 (4 * TCP_MSS)   // 4 KB receive window
#define TCP_SND_BUF             (4 * TCP_MSS)
#define PBUF_POOL_SIZE          16
#define PBUF_POOL_BUFSIZE       1280

#define LWIP_ALTCP              1
#define LWIP_ALTCP_TLS          1   // mbedTLS 연결

4.4 BT → lwIP 통합 — netif driver

BNEP 레이어 위에 lwIP netif 드라이버를 작성. 송신은 linkoutput에서 이더넷 헤더를 만들어 BNEP로 넘기고, 수신은 BNEP 콜백에서 tcpip_input() 호출. 

err_t bnep_netif_output(struct netif *netif, struct pbuf *p) {
    uint8_t buf[1518];
    pbuf_copy_partial(p, buf, p->tot_len, 0);
    bnep_send_compressed(buf, p->tot_len);
    return ERR_OK;
}

void bnep_rx_callback(uint8_t *data, size_t len) {
    struct pbuf *p = pbuf_alloc(PBUF_RAW, len, PBUF_POOL);
    pbuf_take(p, data, len);
    tcpip_input(p, &bnep_netif);
}

5. DHCP / DNS 클라이언트

5.1 DHCP 동작

  1. BNEP 채널 OPEN 직후 lwIP dhcp_start() 호출
  2. DISCOVER 브로드캐스트 (DST = ff:ff:ff:ff:ff:ff)
  3. 호스트 OS 내장 DHCP 서버가 OFFER 응답 — 사설 대역(예: 192.168.44.2/24)
  4. REQUEST → ACK 후 IP 주소 확정
  5. 옵션 6 (DNS 서버 주소), 옵션 3 (Gateway) 수신 → lwIP 라우팅 테이블 설정

5.2 DNS resolver

lwIP DNS는 UDP 53 기반 단순 resolver. 캐시는 8 엔트리, TTL 준수.

BudsAI 서버는 단일 도메인(api.budsai.example)이므로 부팅 시 1회 해석 후 IP 캐싱. 인증서 SAN 검증과 별도.

5.3 IPv6 정책

현재 IPv4 only. 호스트가 IPv6 only인 경우는 거의 없으나, 추후 IPv6 지원 시 lwIP의 SLAAC 활성화 + NDP만 추가 코드 ~3KB.

7. PAN 안 되는 환경 대응

7.1 iOS — Companion App via BLE-IP Proxy

iOS는 NAP 미지원이지만 BLE GATT 위에 IP-over-GATT를 자체 구현할 수 있습니다. Apple은 IPSP(IP Support Profile, BT 4.2+)를 지원하지 않지만, custom service로 IP 프레임을 GATT characteristic write로 보낼 수 있습니다. 다만 이 경로는 백그라운드 동작 제약이 있어 사용자가 BudsAI 앱을 켜 둔 상태에서만 동작 — 따라서 이 fallback은 선택적 옵션.

7.2 eSIM in Buds — 호스트 자체 제거

궁극의 fallback은 버즈에 eSIM을 내장해 셀룰러 모뎀으로 직접 인터넷 접속. 호스트가 필요 없어집니다. 단점은 배터리(셀룰러 RF가 BT의 10배 이상 소모), 단가, 통신 요금. 향후 BudsAI Pro Max 같은 모델에서 검토.

7.3 차량 BT 핸즈프리만 지원 시

차량은 BT HFP(핸즈프리)만 지원하는 경우가 많음. 이 경우 차량을 호스트로 못 씀. 대신 운전자의 폰을 호스트로 동시 페어링(Multi-Point Bluetooth)해서 PAN을 폰으로 라우팅. Buds3+가 이미 지원하는 Multi-Point을 활용.

7.4 호환성 매트릭스 정리

시나리오 → 호스트 채널 최종 인터넷 경로 ───────────────────────────────────────────────────────────────────── 폰(Android/Galaxy) 곁에 있음 → BT PAN to 폰 폰의 4G/5G/WiFi 노트북 곁에 있음 → BT PAN to 노트북 노트북의 LAN MP3/PMP → BT PAN to MP3 MP3의 WiFi 스마트 TV (2024+) → BT PAN to TV TV의 LAN 차량 (PAN 지원) → BT PAN to 차량 차량의 LTE 차량 (PAN 미지원) + 폰 → BT Multi-Point 폰의 4G/5G iPhone 곁에 있음 → BLE-IP Proxy (앱 ON) iPhone의 셀룰러 혼자 외출 (호스트 없음) → eSIM 직결 (Pro 모델) 버즈 셀룰러
관련 문서 호스트 선택 우선순위, 멀티-호스트 핸드오프 로직은 호스트 브릿지 페이지에서 다룹니다.
