1. 레이어 구조

2개 레이어로 나누어 설계. 위는 애플리케이션 레벨 의미, 아래는 BT 전송 단위.

┌─────────────────────────────────────────────┐ │ Session Message (전체 요청 = 수십~수백 KB) │ ← 애플리케이션 레벨 │ ┌─────────┬──────────┬──────────────────┐ │ │ │ Header │ Metadata │ Audio Payload │ │ │ └─────────┴──────────┴──────────────────┘ │ └─────────────────────────────────────────────┘ │ 분할 (fragmentation) ▼ ┌────────────┬────────────┬─────────┬─────────┐ │ Frame #1 │ Frame #2 │ ... │ Frame N │ ← BT 전송 레벨 └────────────┴────────────┴─────────┴─────────┘

2. Session Message

2.1 전체 구조

+--------+--------+------------+----------------+----------------+ | Header | Meta | Track A | Track B | Footer (CRC) | | 16 B | 가변 | (직전사운드) | (질문음성) | 4 B | +--------+--------+------------+----------------+----------------+

2.2 Header (16 bytes, 고정)

OffsetSizeField설명
04Magic0x42 0x55 0x44 0x53 ("BUDS")
41Version프로토콜 버전 (현재 0x01)
51Message Type0x01=요청, 0x02=응답, 0x03=ACK, 0x04=에러
62Flagsbit0: 압축, bit1: 암호화, bit2: TrackA, bit3: TrackB, bit4: 연속세션
84Session IDuint32, 요청별 고유 (랜덤)
124Total Length전체 메시지 바이트 수

2.3 Metadata (가변, TLV 인코딩)

+--------+--------+----------+--------+--------+----------+ | Tag(1B)|Len(2B) | Value... | Tag(1B)|Len(2B) | Value... | +--------+--------+----------+--------+--------+----------+
TagName타입설명
0x01DeviceID16 B (UUID)버즈 시리얼 또는 페어링 UUID
0x02Timestamp8 B (uint64)Unix ms, 트리거 발생 시각
0x03TriggerType1 B0x01=롱프레스, 0x02=트리플탭, ...
0x04TrackA_Codec1 B0x01=Opus, 0x02=AAC, 0x03=PCM
0x05TrackA_SampleRate2 B16000, 24000, 48000 등
0x06TrackA_Duration2 Bms 단위, 보통 15000~30000
0x07TrackA_Offset4 BSession 시작점에서 Track A 시작 오프셋
0x08TrackA_Length4 BTrack A 페이로드 바이트 수
0x09TrackB_Codec1 B동일
0x0ATrackB_SampleRate2 B보통 16000 (STT 용)
0x0BTrackB_Duration2 Bms 단위
0x0CTrackB_Offset4 B
0x0DTrackB_Length4 B
0x0EBatteryLevel1 B0~100%
0x0FFirmwareVersion4 Bmajor.minor.patch.build
0x10Locale2 B"ko", "en" (응답 언어 힌트)
0x11PrevSessionID4 B연속 대화 시 직전 세션 ID
TLV 장점 새 메타데이터 추가 시 버전을 올리지 않고도 확장 가능. 모르는 태그는 무시.

2.4 Audio Payload

  • Track A: 직전 사운드 (Opus, 24~32kbps mono)
  • Track B: 사용자 질문 음성 (Opus, 16kbps mono, 16kHz — STT 최적)
  • 각 Track은 metadata의 Offset/Length로 위치 지정

Opus 선택 이유: 저지연 + 저비트레이트 + 음성/음악 둘 다 잘 인코딩, 버즈 칩셋 대부분 하드웨어 지원.

2.5 Footer (4 bytes)

OffsetSizeField설명
04CRC32Header부터 Track 끝까지의 CRC32 (IEEE 802.3)

3. Frame (BT 전송 레벨)

Session Message가 크기 때문에 BLE/L2CAP MTU에 맞춰 분할 전송. L2CAP CoC 권장 (MTU 협상으로 최대 ~64KB 가능, 보통 512B~1KB 분할).

3.1 Frame 구조

+--------+--------+--------+--------+--------------------------+--------+ | SOF(1B)| Seq(2B)| Total(2B)| Flags(1B)| Payload (가변) |CRC16(2B)| +--------+--------+--------+--------+--------------------------+--------+
OffsetSizeField설명
01SOF0xA5 (Start of Frame, 동기화용)
12Sequint16, 0부터 시작하는 순번
32Total이 세션의 총 프레임 수
51Flagsbit0=마지막프레임, bit1=재전송요청, bit2=ACK필요
6NPayloadSession Message 조각 (보통 N=240~1000)
6+N2CRC16Frame 단위 무결성

3.2 전송 시퀀스

Buds Phone │ Frame 0 (SOF, seq=0, total=20) │ │ ────────────────────────────────>│ │ Frame 1 (seq=1) │ │ ────────────────────────────────>│ │ ... │ │ Frame 19 (seq=19, last=1) │ │ ────────────────────────────────>│ │ ACK (session_id, OK) │ │ <────────────────────────────────│ │ │ ──→ Server │ 응답 프레임들 │ ←── Server │ <────────────────────────────────│

3.3 손실/재전송

  • 호스트(또는 서버)가 Seq 누락 감지 → NAK(seq=N) 전송
  • 버즈가 해당 프레임만 재전송
  • 타임아웃 (예: 3초) 시 전체 세션 폐기

4. 응답 패킷 (서버 → 폰 → 버즈)

요청과 동일한 구조, MessageType=0x02. Payload는 TTS 오디오 + 옵션으로 텍스트.

응답용 추가 Metadata Tag

TagName설명
0x80ResponseTextUTF-8 텍스트 (UI 표시용, 옵션)
0x81TTS_CodecTTS 오디오 코덱
0x82TTS_OffsetTTS 오디오 시작점
0x83TTS_LengthTTS 오디오 길이
0x84Intent인식된 의도 ("song_id", "translate", ...)
0x85Confidence0~100, AI 응답 신뢰도

5. 실제 크기 추정

구간길이/비트레이트크기
Track A: 30초 음악, Opus 32kbps—~120 KB
Track B: 5초 음성, Opus 16kbps—~10 KB
Header + Metadata + Footer—~100 B
요청 총합—~130 KB
L2CAP 1KB MTU 기준—약 130 프레임
1Mbps BLE 처리량 가정—약 1초 전송

6. 보안

  • 세션 키: 페어링 시 ECDH로 합의된 키 사용
  • 암호화: ChaCha20-Poly1305 (Header.Flags bit1=1일 때)
  • 인증: 버즈 ↔ 서버 직접 mTLS(버즈 디바이스 인증서, E2E) — 호스트는 암호문만 봄. 보조 채널(컴패니언 앱)은 JWT 별도 사용

7. 예시 16진 덤프 (요청, 짧은 버전)

42 55 44 53          ; Magic "BUDS"
01                   ; Version 1
01                   ; MsgType: 요청
0C 00                ; Flags: 압축+TrackA+TrackB
A1 B2 C3 D4          ; SessionID
50 FB 01 00          ; TotalLen = 130000

01 00 10 [16B UUID]                   ; DeviceID
02 00 08 [8B timestamp]               ; Timestamp
03 00 01 01                           ; Trigger=롱프레스
04 00 01 01                           ; TrackA Codec=Opus
05 00 02 80 BB                        ; TrackA SR=48000
06 00 02 30 75                        ; TrackA Dur=30000ms
07 00 04 64 00 00 00                  ; TrackA Offset=100
08 00 04 D0 D6 01 00                  ; TrackA Length=120000
... (TrackB 메타) ...

[TrackA Opus 데이터 120000 B]
[TrackB Opus 데이터 10000 B]

XX XX XX XX          ; CRC32

→ 이 패킷이 버즈 내부에서 어떻게 만들어지는지는 펌웨어 페이지, 서버가 어떻게 파싱하는지는 서버 API에서 다룹니다.
