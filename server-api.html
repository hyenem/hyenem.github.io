1. 서버 역할 개요

서버는 패킷 포맷 v1.0의 Session Message를 받아 페이로드를 파싱하고, AI 파이프라인을 거쳐 응답을 생성한 뒤 같은 포맷으로 되돌려줍니다. 가능한 한 응답을 스트리밍으로 내보내 종단간 지연을 최소화합니다.

1.5. 인증 모델 (mTLS + JWT 이중 경로)

서버는 두 가지 클라이언트 종류를 구분하며, 각기 다른 인증 방식을 사용합니다.

클라이언트인증 방식경로접근 권한
버즈 (오디오 세션) mTLS · 디바이스 X.509 인증서 (SE 보관) /v1/stream, /v1/sessions 자기 디바이스의 세션 생성·송수신
컴패니언 앱 (Galaxy UX / 웹 콘솔) JWT (OAuth로 발급) /v1/sessions/{id} 조회, /v1/user/* 자기 계정의 메타데이터 read · 설정 관리

1.5.1 두 경로의 매핑

  • 사용자가 최초 1회 디바이스 인증서를 자기 계정에 연결 (웹 또는 컴패니언 앱)
  • 이후 서버는 mTLS의 디바이스 ID → 사용자 ID 자동 매핑
  • 컴패니언 앱은 OAuth로 받은 JWT로 자기 계정의 히스토리 조회
  • 버즈는 JWT를 갖지 않음 (호스트 노출 표면 축소)
핵심 오디오 페이로드 경로(버즈 ↔ 서버)는 mTLS로 종단간 암호화. 호스트는 평문 못 봄. JWT는 컴패니언 앱의 read-only API용 보조 채널.

5. AI 파이프라인

[Session Message 도착] │ ▼ ┌───────────────────────────┐ │ Track B 분리, Opus 디코딩 │ ~20ms └─────────────┬─────────────┘ ▼ ┌───────────────────────────┐ │ STT (Track B → 질문 텍스트)│ ~150~250ms └─────────────┬─────────────┘ ▼ ┌───────────────────────────┐ │ 의도 분류 (Intent) │ ~30~80ms └─────────────┬─────────────┘ │ ┌──────┴──────┐ ▼ ▼ [Track A 필요?] [Track A 불필요] │ │ ▼ ▼ [Track A 디코딩] [LLM 바로 호출] │ ▼ [의도별 핸들러 실행] ~200~2000ms │ ▼ [응답 텍스트 생성] │ ▼ [TTS 합성, 청크 출력] ~첫 청크 200ms │ ▼ [WebSocket으로 즉시 송신]

5.1 병렬화

  • Track A 디코딩과 STT는 병렬 실행
  • 의도가 결정되면 디코딩된 Track A를 해당 핸들러에 즉시 패스
  • TTS는 응답 텍스트가 일부만 나와도 시작 (LLM 스트리밍 출력 활용)

6. 의도 분류

6.1 분류 방식

경량 LLM 기반 분류기 또는 fine-tuned 텍스트 분류 모델 사용. 입력은 STT 결과 텍스트.

6.2 의도 카테고리

Intent예시 발화핸들러TrackA 필요?
song_id"이 노래 뭐야?"music fingerprint✅
transcribe"방금 뭐라고 했어?"STT(Track A)✅
summarize"방금 한 말 요약해줘"STT + LLM✅
translate"한국어로 번역해줘"STT + Translate✅
define"방금 단어 무슨 뜻?"STT + Dictionary✅
classify"이거 새 소리야?"Audio Classifier✅
recommend"비슷한 거 추천해줘"곡 식별 + Recommender✅
search"이 사건 배경 알려줘"STT + RAG/Web✅
followup"근데 가사도 알려줘"이전 세션 컨텍스트 + LLM❌ (선택)
general"날씨 어때?" (오디오 무관)LLM 직답❌
unclear인식 실패 / 모호"잘 못 들었어요"—

6.3 신뢰도 임계값

  • Confidence ≥ 0.7 → 해당 핸들러 실행
  • 0.4 ≤ Confidence < 0.7 → 핸들러 실행 + 응답에 "혹시 ~을 물어보신 거 맞나요?" 추가
  • Confidence < 0.4 → 재질문 유도

7. 의도별 핸들러

7.1 song_id (음악 식별)

입력: Track A 오디오 (15~30초)

처리: 오디오 fingerprint(Chromaprint, NeuralFP 등) → DB 매칭

출력: 곡명, 아티스트, 앨범, 발매년도

외부: ACRCloud, AudD, 자체 인덱스

7.2 transcribe / summarize / define

입력: Track A 오디오

처리: STT(Whisper급 모델) → 의도에 따라 추가 처리

  • transcribe: 그대로 반환
  • summarize: LLM 요약
  • define: 핵심 단어 추출 → 사전 API

7.3 translate

입력: Track A + 사용자 질문(목표 언어)

처리: STT → 번역 모델(자체 LLM 또는 외부 API)

외부: DeepL, Google Translate, 자체 NMT

7.4 classify (환경음)

입력: Track A 오디오

처리: 오디오 분류 모델 (AudioSet 기반 등) → 라벨 추출

출력: "직박구리 울음소리", "자동차 경적" 등

7.5 recommend

입력: Track A (식별된 곡)

처리: 곡 식별 후 사용자 취향 + 협업 필터링/콘텐츠 기반 추천

7.6 search (외부 정보)

입력: Track A STT 결과 + 사용자 질문

처리: RAG 또는 웹 검색 → 결과를 LLM이 요약·합성

7.7 general (오디오 무관 질문)

입력: 사용자 질문만

처리: LLM 직답 (가벼운 비서 역할)

8. TTS & 응답 스트리밍

8.1 TTS 요구사항

  • 저지연: 첫 청크 ~200ms 이내
  • 스트리밍: 텍스트가 토큰 단위로 들어와도 음성을 동시 생성
  • 형식: Opus 16kHz mono, ~24kbps
  • 음성 다양성: 사용자 설정 가능 (남/여, 톤, 속도)

8.2 LLM ↔ TTS 파이프라인

[LLM 토큰 스트림] ┃ "아이유의" ┃ " 'Love" ┃ " wins all'" ▼ [문장 경계 감지 / 청크 버퍼링] ▼ [TTS 합성: 작은 단위(2~4초)로 청크 출력] ▼ [Opus 인코딩] ▼ [WebSocket binary frame 전송]

8.3 첫 청크 최적화

  • LLM이 첫 문장을 다 만들기 전, 첫 N토큰(예: 6~8단어)이 모이면 즉시 TTS 시작
  • 이후 토큰이 추가되면 연결되는 TTS 청크 생성
  • 사용자 체감 응답 시간 대폭 단축

9. 세션 & 연속 대화

9.1 세션 저장

  • 요청/응답 메타데이터를 Redis에 30분 TTL로 저장
  • 키: session:{session_id} → 사용자ID, 질문 텍스트, 응답 텍스트, 의도, TrackA 식별 결과 등
  • PostgreSQL에는 영구 히스토리 별도 저장 (옵션)

9.2 후속 질문 처리

요청 메타데이터에 PrevSessionID(0x11)가 있으면:

  1. Redis에서 직전 세션 컨텍스트 로드
  2. 현재 Track B(질문)와 함께 LLM에 제공
  3. 의도가 followup이면 Track A 없이도 답변 가능
  4. 응답 후 같은 세션 체인에 추가
// Redis 저장 예시
{
  "session_id": "a1b2c3d4",
  "user_id": "u123",
  "prev_session_id": null,
  "query_text": "이 노래 누구 곡이야?",
  "intent": "song_id",
  "track_a_summary": "music: IU - Love wins all",
  "response_text": "아이유의 'Love wins all'입니다",
  "created_at": 1716297791
}

// 후속 질문 도착 (PrevSessionID = a1b2c3d4)
// LLM 입력 context:
//   "직전 대화: 사용자가 들은 곡은 IU - Love wins all.
//    AI 응답: 아이유의 'Love wins all'입니다.
//    현재 질문: 가사도 알려줘"

10. 성능 목표 & SLA

10.1 지연 예산

단계목표비고
수신 → STT 완료250msTrack B 짧음 (~5초)
STT → 의도 분류80ms경량 모델
핸들러 처리200~1500ms의도별 상이
LLM 첫 토큰300ms스트리밍 시작점
첫 TTS 청크 송신200ms스트리밍
종단(서버 입장): 수신 → 첫 청크 송신<1000ms (p50)
p95<2000ms

10.2 가용성

  • API: 99.9% (월 ~43분 다운)
  • 리전 다중화로 일부 장애 격리
  • 핵심 핸들러(STT/LLM/TTS) 별도 SLO

11. 스케일링

11.1 부하 특성

  • 요청당 GPU 시간: STT ~50ms, LLM ~500ms, TTS ~200ms
  • 피크 시간대: 출퇴근, 점심 (음악·팟캐스트 청취 시간)
  • 요청 크기: ~130KB 업로드, ~60KB 다운로드

11.2 스케일 전략

GPU 워크로드

STT/LLM/TTS는 별도 GPU 풀, 큐 기반 배치 처리. 동적 오토스케일.

CPU 워크로드

API 게이트웨이, 의도 분류는 CPU. K8s HPA로 QPS 기반 스케일.

캐싱

음악 식별 결과(같은 곡 자주 식별됨), 자주 묻는 질문 응답.

WebSocket 분산

스티키 세션, Redis Pub/Sub로 노드 간 응답 라우팅.

11.3 비용 최적화

  • 경량 모델 우선, 필요한 경우만 대형 LLM 호출
  • 의도 분류는 자체 경량 분류기 → 비용 0에 가까움
  • TTS는 자주 쓰는 짧은 응답("잘 못 들었어요" 등) 사전 캐싱
  • 오디오는 처리 후 즉시 삭제 (저장하지 않음)
